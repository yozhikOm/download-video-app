# Backend architecture

The Rust backend in `src-tauri/src/` owns all state. The React UI only shows the events the backend sends and sends commands back. Terms such as Video, Probe, Download, Preset, Partial, Format, Tool, Package, Setup and Sign-in browser are defined in [`GLOSSARY.md`](../GLOSSARY.md).

```
lib.rs (Tauri commands, wiring)
  ├─ Prober ──────┬─ Toolbox ──┬─ Releases   ─ GithubReleases │ FakeReleases
  └─ Downloader ──┤            ├─ Processes  ─ SystemProcesses │ FakeProcesses
                  │            ├─ Clock      ─ SystemClock │ FixedClock
                  │            └─ EventSink
                  ├─ Settings ── EventSink
                  ├─ preset
                  ├─ transcript
                  └─ EventSink  ─ Subscribers (lib.rs) │ RecordingSink
```

## Modules

**`toolbox.rs`: `Toolbox`**
The app's own installed Tools in the app data folder (`tools/`), and the only code that knows which Tools exist and which Package provides each one. It runs Setup: it reads the manifest, checks which Tools are in place, downloads the missing Packages through `Releases`, verifies their SHA-256, and installs them. It also runs a Tool through `Processes`, pointing yt-dlp at the app's own ffmpeg and deno, and at the cookies of the Sign-in browser the caller passes (ADR-0002). When a Tool fails to start, `Toolbox` forgets it and shows the setup screen again. `SetupState` is what the setup screen shows, and every change to it is sent as an event.

**`probe.rs`: `Prober`**
Probes a URL by running `yt-dlp -J` through `Toolbox`, with the Sign-in browser from `Settings` when one is chosen and the URL is YouTube's, and keeps what it learned as a `Video` (Formats, Transcript languages, original language, chapters, whether it was a stream) for the Download. Only the latest Probe counts: a late answer to an older one is dropped. `ProbeState` is what the main screen shows: the Video's card with the Video presets it has and the one chosen at first, its Audio presets and whether M4A saves its sound as it is, the languages it has a Transcript in and the one chosen at first, or a `ProbeError` for a playlist or channel, a stream that is live now, a Video that needs signing in, YouTube's bot check, a Sign-in browser whose cookies yt-dlp can't read (and why), a URL whose Video id was cut off, or an unsupported URL, along with the Sign-in browser the Probe ran with. When yt-dlp fails to start, `Prober` drops the Probe and runs Setup to restore it. Its tests (`probe/tests.rs`) feed real yt-dlp answers from `probe/fixtures/` through `FakeProcesses`.

**`preset.rs`: `Preset`, `VideoPreset`, `AudioPreset`**
The Presets and which of them a Video has. A `Preset` is either group, known to the UI and in a Partial's name by its own name (`1080p`, `mp3`). A Video has both Audio presets, M4A and MP3, when some Format has sound or doesn't tell, or when the site lists no Formats, and none when every Format is without sound. M4A saves the sound as it is when some Format has AAC sound (`mp4a.*`), and the UI calls it «M4A (оригинал)» only then. A Preset counts resolution as yt-dlp's `res` does, by the smaller side of the picture, so that a vertical 1080×1920 is 1080p. A Video has a Preset when one of its video Formats reaches the Preset's resolution but not the next one up (1080p takes 721–1080, so a widescreen 1920×800 is 1080p too; 480p takes 361–480, 360p takes all below). Only video-only Formats count when the Video has any, since a Download takes one of them rather than a Format with video and sound together. «Лучшее» is offered only when it saves more than the highest of them, above 2160p, or when the Video has no other (its Formats are of unknown size), since otherwise the highest saves the same. The one chosen at first is 1080p, or the nearest lower one the Video has, or the nearest higher one when it has none lower, or «Лучшее» when it has no other.

**`transcript.rs`: `TranscriptLanguage`**
The languages a Video has a Transcript in, and turning subtitles into its text. A language comes from the subtitles the author added or, when they have none in it, from the captions the site generated. Machine translations are never offered: YouTube lists its captions of what is spoken under `<language>-orig` among their translations into every other language, so when the captions have such a language, only it counts. The one chosen at first is the Video's own language (a regional variant such as `en-GB` counts as `en`), by subtitles over captions and the exact language over a variant; when the Video's language is unknown or has no Transcript, that of the captions, which are of what is spoken; otherwise the first language. The text of WebVTT subtitles is each line of each cue without the timing, tags and cue ids, one per line; a line that repeats the one before it is dropped, since YouTube's captions show each line again in the next cue.

**`download.rs`: `Downloader`**
Downloads the Video the latest Probe found with a Video preset as an MP4, or with an Audio preset as the sound alone, with or without its Transcript, or its Transcript alone (`Content`), through `Toolbox` with the Sign-in browser from `Settings` when the URL is YouTube's, as `Prober` does. The Preset becomes yt-dlp's Format order (`-S res:<resolution>,vcodec:h264,acodec:aac`, plain `res` for «Лучшее»): the highest resolution up to the Preset's, then H.264 and AAC over VP9, AV1 and Opus of the same resolution; above 1080p YouTube has only VP9 and AV1. yt-dlp takes separate video and audio (`-f bv+ba/b`), since preferring AAC would otherwise pick a Format with both, which YouTube sends slowly over HLS; a site with only such Formats falls back to the best of them. ffmpeg merges the video and audio into an MP4. An Audio preset takes the best sound alone (`-f ba/b`, a Format with both on a site without one) and has ffmpeg extract it (`-x`): M4A prefers AAC (`-S acodec:aac`), which ffmpeg copies into the M4A without encoding it again, and only a site without AAC gets its sound encoded, as AAC at 192 kbit/s (`--audio-quality 192K`, which yt-dlp ignores when it copies); MP3 takes the best sound and encodes it as LAME's VBR quality 1 (`--audio-quality 1`, about 190–250 kbit/s). yt-dlp works in the `partials/` folder in the app data folder, dating its files when it receives them (`--no-mtime`) rather than as the site last changed the Video, under a name made of the Video's id and the Preset (`<id>.<preset>.<ext>`, such as `<id>.1080p.mp4` or `<id>.mp3.webm`), never the title, so that a later Download of the same Video with the same Preset can resume. yt-dlp reports on stdout, read line by line as it arrives: the separate Formats it is about to receive with their sizes, then a JSON progress line per chunk (`--progress-template`) naming the Format being received and its video codec, `none` for the sound alone, so that one percent and time left cover all of them (a Format that comes in fragments, such as HLS, counts by the share of fragments received, since its size is only an estimate, far too small at first), `[processing]` right before ffmpeg merges the video and audio or extracts the sound, and the final file's path as a JSON string. A Transcript is received first, so that a Download whose Transcript fails doesn't receive the media for nothing: yt-dlp downloads the subtitles (`--write-subs`) or captions (`--write-auto-subs`) of the language alone (`--skip-download`), as WebVTT (`--sub-format vtt`, converted by ffmpeg with `--convert-subs vtt` when the site has none), to `<id>.transcript.<language>.vtt` in `partials/` (`-o subtitle:%(id)s.transcript.%(ext)s`). Without the media yt-dlp prints no path, and it succeeds without a file when the site has no subtitles in the language, so the file is looked for by that name; the Download fails without it. `Downloader` writes its text next to it as `.txt` and removes the subtitles. When yt-dlp ends, `Downloader` moves the files to the save folder (the user's Downloads folder; when the system doesn't report one, `~/Downloads`, then `downloads/` in the app data folder) under the Video's title, the Transcript under the same name as the media, with the characters Windows forbids replaced by lookalikes and " (1)", " (2)"… on a clash of either, so that the two keep the same name; it never overwrites a file. `Downloader` keeps the Queue, which lives only as long as the app runs: `add` puts a Download at its end as Queued, and `run` receives the Queued ones one at a time in the order of the Queue until none waits; a second `run` meanwhile returns at once, and a Download added meanwhile is received by the first. The worker gives up only under the Queue's lock, so that an added Download never waits with no worker. A Download of the same Video (by its id) with the same Preset, or of its Transcript alone in the same language, isn't added while one is Queued, Downloading or Processing (`Added::Duplicate`); with another Preset, or once the first is Done, Failed or Cancelled, it is. Every change to the Queue is sent whole as an event. `Download` is what the main screen shows of each: its id in the Queue, the Video's card, its Preset and Transcript language, and its status (Queued, Downloading with what it receives now, the Transcript, the video or the audio, and percent, speed and time left, Processing, Done with the saved media, or the Transcript when it is alone, Failed, or Cancelled). A Done, Failed or Cancelled Download can be taken out of the Queue (`remove`, and `clear_done` for the Done ones); its files stay, and so does a Failed one's Partial, which a later Download of the same Video with the same Preset resumes. A Queued or Downloading Download can be cancelled (`cancel`); one Processing can't, since ffmpeg is about to make its file. A Queued one's Partial is removed at once, save for the files of a Transcript the running Download receives as well; a Downloading one's yt-dlp is killed through a `Stopper`, with the ffmpeg it runs, and its Partial is removed once it has exited, so that nothing has the files open; one killed and then found broken stays Cancelled, and the next Download tells whether yt-dlp is broken. Once yt-dlp has ended, the Download can no longer be cancelled. A Failed Download keeps its Partial, save for the part, the media or the Transcript, that yt-dlp failed with HTTP Error 416: that is how yt-dlp fails when the part is already whole, asking for the bytes past its end without telling it is done (yt-dlp#12994), so every retry would fail the same way and the next one receives that part from scratch. Retrying a Failed Download, or a Cancelled one once its yt-dlp has exited, puts it back at the end of the Queue, unless that would be a duplicate, to download its own Video with its own Preset and Transcript again, so that yt-dlp resumes from a Failed one's Partial and starts a Cancelled one from scratch; a Cancelled one's Partial is removed again first, in case a file of it was still open when it was cancelled. At launch, `discard_old_partials` removes the Partials untouched for more than 7 days by the `Clock`. When yt-dlp fails to start, `Downloader` drops the Download and runs Setup to restore it, or waits for the Setup already running; the Queue goes on once Setup ends Ready, and otherwise waits until Setup is retried. Its tests (`download/tests.rs`) run a fake yt-dlp through `FakeProcesses` that writes its file, or subtitles from `download/fixtures/`, where it is told, and may cancel its own Download while it runs.

**`settings.rs`: `Settings`**
The app's settings in `settings.json` in the app data folder; today only the Sign-in browser, which it gives only for a YouTube URL. A missing or unreadable file means the defaults. Every change is saved at once and sent as an event; a change that can't be saved changes nothing. Its tests (`settings/tests.rs`) relaunch on the same folder.

**`releases.rs`: `Releases`**
The only code that talks to the network: it asks for a Package's latest release (`latest_release`) and streams an asset to a writer (`fetch`). It does not know where files go or what a Tool is. `GithubReleases` (`releases/github.rs`) uses the official GitHub releases of yt-dlp, FFmpeg-Builds and deno, and reads each one's checksums file. `FakeReleases` (`releases/fake.rs`) publishes small fake releases, and a test can make it go offline, publish a wrong checksum or point to an unofficial asset.

**`processes.rs`: `Processes`**
The only code that starts Tools: `run` takes a path and arguments and waits for the program to exit; `run_streaming` also hands each stdout line to a callback as soon as it is printed, and a `Stopper` kills the program from another thread, at once when it was stopped before the program started, until the caller finishes it. It does not know which Tool it is running. `SystemProcesses` starts the program without a console window and kills it with the programs it started (`taskkill /T`, waited for, so that they are gone by the time it returns), since yt-dlp's ffmpeg would otherwise keep its files open; its tests (`processes/tests.rs`) stop a `ping` that `cmd` started, and remove the file `ping` writes as soon as the stopped run returns. `FakeProcesses` (`processes/fake.rs`) records what was started and answers with scripted output, or with what a script returns for the arguments, counts the programs killed while they ran, and a test can make a Tool fail to start.

**`clock.rs`: `Clock`**
The current time, so tests can fix it (`FixedClock`).

**`events.rs`: `AppEvent`, `EventSink`**
Events from the backend to the UI. `Subscribers` in `lib.rs` forwards them to the UI channels. In tests, `RecordingSink` collects them.

**`lib.rs`**
Tauri commands (`app_info`, `subscribe`, `retry_setup`, `probe`, `set_sign_in_browser`, `add_download`, `retry_download`, `cancel_download`, `remove_download`, `clear_done_downloads`, `open_downloaded_file`, `show_downloaded_file`) and wiring: it creates the `Settings`, the `Toolbox`, the `Prober` and the `Downloader` with the real implementations, discards the old Partials before the UI can add a Download, and starts Setup in the background on launch. The `add_download` command takes a Video or Audio preset, a Transcript language, or both, refuses a Preset or language the probed Video doesn't have, and answers whether the Download was Queued or a duplicate, and of which Download, so that the UI warns only while that one is Queued or running; it and `retry_download` run the Queue in the background, and `retry_setup` runs it once Setup ends Ready. The commands about one Download name it by its id in the Queue. The Done Download's file is opened in its default program and shown in Explorer through the opener plugin; that is the user's file, not a Tool, so it doesn't go through `Processes`. The backend picks the file, so that the UI never names a path to open.

## Seams

`Releases`, `Processes`, `Clock` and `EventSink` are traits so that `Toolbox`, `Prober` and `Downloader` can be tested without the network, real programs or the real time (`toolbox/tests.rs`, `probe/tests.rs`, `download/tests.rs`). Code that needs the network or runs a Tool goes through one of these traits, never around it.
